# 项目需求文档

## 1. 背景与目标

AQM 是一个多智能体编排控制台。本次新增「任务导出」功能：把一个任务的会议记录、阶段输出、工作块、审批记录四类产物导出为一份 Markdown 归档文件，供分享与复盘使用。

会议在动设计前，先由四位成员核对了当前工作区的盘面事实，这些事实构成本需求的硬约束：

- `.aqm/meetings/<task_id>/` 下目前只有 `meta.json` 与 `meeting.md` 两个文件。`meta.json` 内含 `current_round`、`rounds_completed`、`agents[].status`、`timeout_per_agent`、`shared_file`，以及 `agents[].output` / `thinking` / `actions` 三段全量文本。
- **议题点名的四类产物中，只有「会议记录」有存储契约。** 阶段输出、工作块、审批记录在盘面上没有任何落盘痕迹；工作块与审批的唯一候选契约是 `.aqm/queue.db` 的 `tasks.data`（TEXT，JSON blob），而该表当前 0 行。
- `meeting.md` 中每个 agent 的发言正文与 `meta.json.agents[].output` 是**同一事件的双写**，不是互补关系。
- `meta.json` 是被编排运行时持续写入的**活文件**（`status`、`current_agent_index`、`rounds` 每轮都在变），且 `rounds` 与 `current_round` 语义重叠并存，写侧已在漂移。
- `meta.json` 只有轮次号数组 `rounds_completed: [1]` + 单个 `current_round`，**没有 agent × round 的完成矩阵**。

**目标**：产出一份可被肉眼读懂、可被脚本二次消费、且在数据残缺时不会「看起来对、实际错」的 Markdown 归档。会议明确：这个功能真正的工程量不在渲染（渲染器不到 200 行），而在**去重规则、轮次边界、字段白名单**这三件「读侧语义」上；弄错这三件，产出的是一份看起来漂亮、实际自相矛盾的归档，会被当真。

**威胁模型定位（审核方结论，贯穿全文）**：本功能本质是**新增了一条外发数据通道**（分享按钮 + `aq<path>` 链接 + 归档文件本体），因此不应作为「便利功能」评审，而应作为**安全控制**评审——要回答「什么东西离开大楼、谁能触发、绕过它有多容易」。

## 2. 范围（包含 / 不包含）

**包含**

- 统一的只读产物视图层 `TaskArtifact` 抽象，导出器只依赖该视图，不依赖任何一类产物的落盘方式。
- 三类产物各自的读取源（会议记录 = `meta.json` + `meeting.md`；阶段输出 / 工作块 / 审批 = 本轮 `NullSource` 降级源）。
- 一致性快照采集、去重与漂移检测、轮次结构解析、确定性截断。
- 单文件 Markdown 与「目录归档 + `index.md`」两种输出形态，以及字段白名单式脱敏管线。
- 机器可读元信息头、`manifest` 清单、可注入时钟的幂等性保证。
- UI：任务级与节级双入口、导出前「分享安全体检」首屏、导出后结果面板、目录导航、导出进度、导出历史、键盘可访问性。
- 原子写盘与 Windows 平台现实处理。
- **前置契约工作**：写侧 per-agent 完成态的落盘契约必须在本轮定稿（详见未决问题 Q1，审核方判定其为前置依赖而非可选项）。

**不包含**

- 阶段输出 / 工作块 / 审批的**存储契约建设本身**（本轮只以降级源接入，产物落盘由写侧另行推进）。
- 写侧 `rounds` 与 `current_round` 语义重叠的整改（只在本文档记录为已知问题，不在本功能内修）。
- 显式 `--summarize` 摘要模式的具体实现（本轮只做确定性截断；是否纳入本期见未决问题 Q5）。
- 归档的**导入 / 回读**（仅保留 `aq<path>` 链接的回跳入口，导入器不在本期）。
- 对 `.aqm/` 目录裸存敏感数据的整改（导出侧只加显式告警，见 FR-21）。

## 3. 功能需求

### 3.1 产物视图层与快照

**FR-01｜`TaskArtifact` 抽象**
定义统一产物结构 `{kind: meeting|stage_output|work_block|approval, task_id, seq, started_at, finished_at, content_ref, hash}`；每类产物实现同一个只读接口 `load(taskId) -> Artifact[]`。导出器只允许依赖该视图，禁止直接写死读取 `.aqm/xxx` 路径。验收方式：在阶段输出由「进程内状态」迁到「磁盘」时，导出功能零改动。

**FR-02｜快照必须是一次性读取的纯函数**
采集阶段先对各源文件做一次性 `read_bytes`，对每份源算 sha256 记入 `manifest`，之后**所有渲染只基于这些内存 buffer，中途不得再碰磁盘**。导出语义为「截至第 N 轮的快照」而非「此刻的进程状态」，该语义必须写入导出文件的元信息。

**FR-03｜三阶段管线与双 sink**
实现为三个纯函数：`collect(task_id) -> Snapshot`（只读、无副作用）、`render(snapshot, opts) -> Iterator[str]`（生成器，按节 yield）、`write_stream(it, sink) -> Manifest`。输出器从第一天起按「分节 + 索引」的中间结构生成，单文件与「目录归档 + `index.md` + `NN-*.md`」都只是 `write_stream` 的消费者。

**FR-04｜`--dry-run` 与真实导出走同一条管线**
`--dry-run` 不得单独实现一条渲染路径，必须实现为 `write_stream(it, NullSink())` 后打印 `manifest`。验收方式：dry-run 预览与真实产物除文件名外不得出现格式差异。

**FR-05｜CLI 退出码语义**
`0` 完整导出；`2` 任务不存在；`3` 部分产物缺失（仍写出了文件）；`4` 写盘失败。调用方不得需要解析 Markdown 才能判断结果。

### 3.2 去重、漂移检测与结构解析

**FR-06｜去重是 P0**
`meeting.md` 是逐轮发言的**权威源**，`meta.json.agents[].output` 仅在其缺失或被截断时作为 fallback 启用；`manifest` 必须记 `output_source: meeting|meta_fallback`。禁止出现「渲染一遍 `meta.json` 再贴一遍 `meeting.md`」的实现。

**FR-07｜漂移检测**
用 `output` 的块首行与块末 32 字符对 `meeting.md` 对应段落做**双端比对**（不采用单一 64 字符前缀，因双写崩溃点恰恰出现在「前 64 字相同、后文分叉」时）。不一致则 `manifest` 记 `drift: true`；fallback 被触发时记 `fallback_reason: truncated`。

**FR-08｜逐轮结构解析边界**
逐轮结构只能从 `meeting.md` 的标题解析，`meta.json` 中没有 per-round 的 output 数组。解析正则采用 `^### (.+?) \(([A-Za-z0-9_-]+)\) - 第(\d+)轮$`：名字段非贪婪且不得跨行，agent id 段限定 `[A-Za-z0-9_-]`。扫描起点为**第一个 `\n---\n` 之后**，避免议题正文中同格式的行被误当结构。

**FR-09｜解析失败的降级行为**
解析失败不抛异常，退化为「整篇作为单节附录」并令 `manifest` 记 `structure: degraded`；该降级状态必须**同步触发导出前体检首屏的红字提示**（见 FR-26），不得只写进 `manifest` 让用户事后才发现。

### 3.3 章节范围与完整性标记

**FR-10｜缺失产物的降级声明**
阶段输出 / 工作块 / 审批各配一个 `NullSource`：`load()` 返回 `[]`，`manifest` 写 `{kind, status: "source_unavailable", reason: "no_storage_contract"}`，正文该节渲染为引用块 `> 本节无数据：approvals 尚未落盘`。缺失产物不得阻塞导出发布。

**FR-11｜完整性标记必须机器可读且肉眼可见**
`manifest` 必须包含 `completeness: {kinds_present, kinds_missing}`；**文件名或一级标题**必须直接带可见标记（如 `[PARTIAL: approvals, stage_output]`），不得只藏在 `manifest` 里。

**FR-12｜节级导出**
除任务级全量导出外，会议记录、阶段输出、工作块、审批各 tab 头部提供「导出本节」入口，复用同一管线，仅增加一个 `scope` 参数。

### 3.4 文档形态与渲染

**FR-13｜按可读文档而非数据 dump 设计**
一级标题 = 任务名 + 快照轮次；二级 = 四大节；三级 = 第 N 轮。agent 发言使用引用块形式 `> **claude**（role）`；每个 agent 块首行放状态徽章（✓ completed / ⏳ running / ✗ failed），**使用 emoji 而非颜色**（暗色终端中颜色不可靠）；轮次之间用 `---` 分隔（与 FR-08 的解析边界复用同一规则）。

**FR-14｜导航**
导出 Markdown 顶部放一行 `[[_TOC_]]`；导出对话框提供「目录预览」侧栏，按二级标题生成可点击锚点列表；目录归档模式下 `index.md` 本身即为导航首页。导航在 UI 预览与文档内部两侧都给到。

**FR-15｜版本头与契约**
导出文件头部放机器可读元信息块：`aqm/export@1`、`schema_version`、`task_id`、`snapshot_round`、`generated_at`、各节字节数与 sha256。理由：归档会被复盘与二次消费（grep、脚本、下次导入），无版本头则半年后无人敢改。

**FR-16｜`manifest` 输出**
「导出成功」不得只以文件写出为准，必须输出 `manifest`（清单 + 各节计数 + 校验和），否则静默丢节不会有人发现。

**FR-17｜幂等性**
文件名带任务 id 与快照标识；重复导出**覆盖自己那一轮的文件**，不去改动已有归档。

**FR-18｜截断必须对齐 block 边界**
`--max-chars` 的截断粒度为「agent 块」，不得在块内按任意字符数硬切。超长时整块只保留首 N 行并插 `… [truncated N chars]` 标记。禁止产出半句话或断裂的引用块。

### 3.5 脱敏与外发控制

**FR-19｜字段白名单（不用正则黑名单）**
`meta.json` 会持续加新字段，黑名单永远漏。导出侧仅允许以下键外发：`id` / `name` / `role` / `runtime` / `model` / `status` / `started_at` / `finished_at` / `output` / `error`（首行）/ `rounds_completed`。明确排除 `system_prompt`、`thinking`、`actions` 全量、`project_dir`。

**FR-20｜`thinking` 默认整段丢弃**
`thinking` 是最大泄漏面（含内部推理、工具原始输出与绝对路径），默认整段丢弃而非「摘要后保留」；保留需显式传 `--include-thinking`。

**FR-21｜路径脱敏可配置**
`--path-mode relative|hash|drop`，默认 `relative`（相对 `project_dir`）。`<demo-project>` 这类前缀对复盘无信息量、对分享是泄漏。

**FR-22｜哈希算在脱敏之后**
sha256 在脱敏之后计算，且哈希那一行**不自参与**自身哈希（否则哈希本身成为原文指纹）。

**FR-23｜源存储未脱敏的显式告警**
`manifest` 必须携带 `source_store: unredacted, path: .aqm/...` 显式告警。导出文件干净 ≠ 系统安全：`.aqm/` 下 `meta.json`、`meeting.md`、`queue.db` 仍裸存 token、绝对路径与 `thinking` 原始输出，且有人会绕过导出器直接拷贝 `.aqm` 目录。根因必须写在产物上，不得让用户误以为「走了导出就安全了」。

### 3.6 界面需求

**FR-24｜任务级 + 节级双入口**
任务详情页右上角放「导出」主入口（低频、全量、复盘场景）；四个 tab 头部放「导出本节」次级入口（高频、轻量、随手分享）。不得只给全量入口而逼用户导出几百 KB 文件再手动裁剪。

**FR-25｜导出前「分享安全体检」首屏（UX P0）**
对话框打开即做一次 dry-run 扫描并展示：各节状态（如「会议记录 12 节 ✓ / 阶段输出 0 节·无数据 / 工作块 3 节·含 2 处路径 / 审批 0 节·未落盘」）、将脱敏项统计（如「将脱敏 N 项：3 个 token、2 个绝对路径、1 段 thinking」）、以及每个可开关项（`--include-thinking`、`--path-mode`）。用户确认后才真正生成。等于把 dry-run 从 CLI 参数升级为 UI 首屏。

**FR-26｜降级与异常状态必须上首屏**
`structure: degraded`、`drift: true`、`source_unavailable` 等状态必须在体检首屏以红字/醒目形式呈现，不得只落在 `manifest`（与 FR-09 联动）。

**FR-27｜缺数据呈现的一致性**
无数据的节，导出预览首屏显示灰色「0 节 · 尚无存储契约」，最终 Markdown 渲染为灰色引用块 `> 本节无数据：approvals 尚未落盘`，**不是空节**。禁止出现 UI 说「审批 0 节」而 Markdown 整节消失的情况——这是最隐蔽的信任流失。

**FR-28｜导出结果面板**
导出完成后展示结果面板：文件名（slug 化 + 时间戳）、各节字节数与 sha256（把 `manifest` 可视化为小表）、「复制链接 / 在文件夹中显示 / 再次导出」。「复制链接」复制 `aq<path><task_id>/<snapshot_round>` 内部协议链接，使复盘者可从文档一键跳回 AQM 对应轮次。

**FR-29｜进度绑定到落盘完成**
超过 2–3 秒时显示按节进度（「正在渲染第 12/14 节…」），消费 FR-03 的生成器按节更新，不让按钮空转。**100% 必须绑定在 `os.replace` 成功之后，而非 `write_stream` 结束**——否则用户会在文件未落盘时提前关窗。

**FR-30｜预览与真实产物同源**
对话框预览区直接消费 `render(snapshot, opts)` 生成器的前 N 行（前 200 行 + 「…共 14 节 480KB，点击生成完整文件」），不得另写一个 Markdown 渲染器。附带收益：首屏响应从「等整个快照 + 渲染完」变为「等第一行」。

**FR-31｜导出历史可见**
任务详情页加「导出记录」折叠区，列出每次导出的文件名、快照轮次、大小、脱敏数、生成时间，每条可重新下载或删除。历史记录存元信息，文件本体按快照轮次覆盖，两者并行不冲突。

**FR-32｜可访问性**
导出必须键盘可达：`E` 快捷键（聚焦任务卡片时）、Enter 打开对话框、Tab 顺序走完选项、Esc 关闭。所有状态徽章配 `aria-label`，颜色不作唯一语义载体（emoji + 文本双编码）。对话框须处理焦点陷阱，键盘用户不得被困在 modal 中。

### 3.7 写盘

**FR-33｜原子替换**
同目录 `dest + f".{os.getpid()}.tmp"` → `flush` → `os.replace`。用 pid 而非固定 `.tmp`，否则并发导出互相踩踏。

**FR-34｜Windows `PermissionError` 重试**
目标文件被其他程序打开时 `os.replace` 会抛 `PermissionError`，须 retry 3 次退避；仍失败则**报错**，不得静默保留 tmp 文件。

**FR-35｜编码与换行统一**
UTF-8 无 BOM、`\n` 换行、末尾单换行。三条不做，git diff 与跨平台预览都会难看。

**FR-36｜路径长度防护**
任务名进入文件名时必须 slug 化并限长 80，防止超过 260 字符的路径上限。

### 3.8 性能与可测性

**FR-37｜导出路径默认禁止任何 LLM 调用**
真实性能风险不在写盘（几百 KB 是毫秒级），而在「要不要为摘要调一次模型」。默认路径零 LLM 调用；`--max-chars` 只做确定性截断；需要摘要须显式 `--summarize` 并接受其慢。此项直接消解长任务运行时长约束下的导出超时风险。

**FR-38｜时间可注入**
`generated_at` 必须来自参数或可注入的 clock，不得直接 `datetime.now()`，否则无法编写 golden test。

## 4. 非功能需求

**NFR-01｜幂等性与字节稳定性**
同一 fixture 跑两次，除 `generated_at` 外字节完全一致。该保证须在**路径归一化之后**仍然成立（见 NFR-02）。

**NFR-02｜哈希可移植性**
`--path-mode relative` 的相对化依赖 `project_dir`，而 `project_dir` 在 A 机与 B 机不同，导致同一逻辑快照换机导出 sha256 变化，废掉「可 diff / 幂等」。要求：`manifest` 记录 `path_mode` + `project_dir_slug`，或哈希算在**归一化形式**（全相对化）上，并注明哈希的适用域。

**NFR-03｜安全控制级评审**
本功能按安全控制而非便利功能评审。脱敏管线与导出同批交付，不得后置；脱敏完成不得被表述为「系统已安全」。

**NFR-04｜外发通道可控性**
产物必须显式声明 `source_store: unredacted`（FR-23），使「导出文件干净」与「`.aqm/` 目录仍可被整包拷走」这两个事实同时可见。

**NFR-05｜部分失败可观测**
`manifest` 与退出码共同承担可观测性；静默丢节、静默选错源、静默覆盖旧快照均不得发生而无痕。

**NFR-06｜跨端渲染兼容**
Markdown 形态须在 GitHub / GitLab / Notion / 暗色终端中一致可读；语义标记只用跨端稳定的手段（层级、引用块、emoji + 文本双编码）。

**NFR-07｜长文档可用性**
几百 KB 单文件不得无导航可用；UI 预览与文档内部两处均须提供导航。

## 5. 验收标准

**AC-01｜golden 测试**
同一 fixture 导出两次，除 `generated_at` 外字节完全一致；且该断言在路径归一化后仍成立（对应 NFR-02）。

**AC-02｜三类 fixture**
已完成任务、进行中任务（即当前这个）、缺 `meeting.md` 的任务，三者均须跑绿。

**AC-03｜泄漏模式断言**
导出产物断言不含 `[A-Z]:\\`、`/home/`、`sk-`、`ghp_`、`AKIA`。

**AC-04｜边界负例矩阵（须全部跑绿）**

| 编号 | 负例 |
|---|---|
| 1 | `meeting.md` 存在但 0 字节 |
| 2 | 某 agent `status: failed` 停在轮中（快照是否含其半截 output —— 见 Q2） |
| 3 | 两个 agent 同名 / 同 id（正则分组与引用块归属串位） |
| 4 | agent 名含 `)`、`第`、全角字符（直接触发 FR-08 的 id 段与名字段脆弱性） |
| 5 | `finished_at < started_at` 或跨时区（快照排序边界） |
| 6 | `queue.db` 的 `tasks.data` 有行但对应任务无行（当前 0 行的退化情形） |
| 7 | `data` blob 含非 UTF-8 / 二进制（decode 中途抛错、导出半截崩溃） |
| 8 | 同任务同轮被两个用户并发导出（last-writer-wins 静默覆盖，共享归档竞态 —— 见 Q6） |
| 9 | 目标文件被本 App 预览器或导出历史「重新下载」锁住（`os.replace` 的外部锁，retry 救不了「用户正在读」） |

**AC-05｜UX 三条**
导出前用户知道会分享什么；导出后用户知道得到了什么；文档内用户能顺着层级读完。

**AC-06｜可访问性**
FR-32 所列键盘路径与 `aria-label`、焦点陷阱全部通过 QA。

**AC-07｜审核方放行门槛（未满足不发布）**
- Q1 必须有源：要么写侧落 per-agent 完成态，要么 `manifest` 诚实标 `complete_rounds: unknown`，**绝不出 `complete_rounds: N` 这类猜测数**；
- FR-11 的机器可读 `completeness` + 可见 `PARTIAL` 标记必须进文件名 / 一级标题，不得只藏 `manifest`；
- AC-04 中第 1、4、7、9 四个负例跑绿，且 AC-01 的 golden 测试在路径归一化后仍成立。

## 6. 未决问题

**Q1｜per-agent 完成态从哪来（阻塞项，P0）**
`snapshot_round` 与「剔除最后一个未完成整轮」在当前数据模型下算不出来：`meta.json` 只有 `rounds_completed: [1]` 与单个 `current_round`，没有 agent × round 的完成矩阵。实现时无源可查——只知道当前到第几轮，不知道第 1 轮里 `finished_at: null` 是否意味着该 agent 没写完。若照现状实现，`manifest` 里的 `complete_rounds` 就是猜的，而这恰恰触发「归档自相矛盾」这一最坏结果。两种解法：**(a)** 写侧把 per-agent 完成态落到磁盘（审核方判定为前置依赖，非可选项）；**(b)** `manifest` 诚实写 `complete_rounds: unknown`。本轮须定稿选哪条。

**Q2｜failed agent 的半截 output 是否进入快照**
负例矩阵第 2 项：某 agent `status: failed` 停在轮中时，快照是否包含其半截 output。它与 Q1 直接耦合——在缺少完成矩阵时，「未完成整轮剔除」这条规则无从判定，需要与 Q1 一并给出裁决。

**Q3｜阶段输出 / 工作块 / 审批的落盘契约**
需确认这三类产物目前到底是**进程内状态**还是**已经落盘**，这决定 FR-01 读接口如何取数。工作块与审批的唯一候选契约是 `.aqm/queue.db` 的 `tasks.data`（当前 0 行），是否为既定存储方案尚不确定。

**Q4｜文件名命名规则二选一**
「文件名带快照**时间**」与「重复导出**覆盖**自己那一轮」相互矛盾：按时间命名则两次导出产生两个文件、目录无限堆积；按轮次命名则第二轮会静默覆盖第一轮。审核方判断复盘要的是**版本**而非时间快照，倾向「轮次命名 + 覆盖」，但该项尚未在讨论中定死，须裁决。

**Q5｜`--summarize` 摘要模式是否纳入本期**
已达成的是「导出路径默认零 LLM 调用、`--max-chars` 只做确定性截断」。但显式 `--summarize` 模式本身是否在本期交付，会议未定。

**Q6｜并发导出的仲裁策略**
负例矩阵第 8 项：同任务同轮被两用户并发导出时，目前是 last-writer-wins 静默覆盖。需要裁决是加锁、加内容寻址，还是显式提示覆盖。

**Q7｜外部锁无法重试时的用户处置**
负例矩阵第 9 项：目标文件被本 App 自己的预览器或导出历史锁住时，FR-34 的 3 次退避救不了「用户正在读」这种情况。需要裁决是提示用户关闭、改写到新文件名，还是报错退出。

**Q8｜写侧字段语义重叠的归属**
`meta.json` 中 `rounds` 与 `current_round` 语义重叠且同时存在，属写侧漂移。本功能不含整改，但需确认导出侧是否要在渲染层做一次性归一化，以免把漂移直接搬进归档。

**Q9｜凭据模式清单的完整性**
AC-03 目前只覆盖 `[A-Z]:\\`、`/home/`、`sk-`、`ghp_`、`AKIA` 五个模式。脱敏用字段白名单（FR-19）规避了字段级漏配，但白名单外的自由文本（如 `output` 正文）中还有哪些凭据模式需要匹配，清单待补。
